📚 Guia de Mocks

O que é o Mock Manager?

O Mock Manager é uma interface para criar e gerenciar mocks de APIs e eventos Kafka armazenados no MongoDB. Ele permite simular respostas de serviços externos e internos sem precisar subir dependências reais.

Os 3 tipos de mock de API
👤 Por Usuário

Retorna payloads diferentes por identificador (orderId, userId, etc). O client consulta o MongoDB antes de fazer a chamada real.

🌐 WebClient Genérico

Fallback do Por Usuário. Mesmo endpoint, mesmo client mock — retornado quando nenhum mock por usuário corresponde ao identificador.

🔖 X-MOCK-ID

Intercepta requisições recebidas pelo próprio serviço. O cliente envia o header X-MOCK-ID e recebe o payload diretamente.

Hierarquia de prioridade (mesmo endpoint)

A hierarquia é resolvida dentro do mesmo client mock pelo GetExternalMockByIdImpl — não há dois caminhos separados:

1
👤 Por Usuário
Busca por endpointId + userIdentifier em allowedUsers
▼ null — não encontrou para esse identificador
2
🌐 WebClient Genérico (fallback)
Busca por _id = endpointId — mesmo documento, mesmo endpoint
▼ null — não encontrou fallback
✕
Retorna null → MockNotFoundException
Nenhum mock encontrado para esse endpoint + identificador
⚠️ Para o fallback funcionar, o _id do WebClient Genérico deve ser idêntico ao endpointId passado no client mock — ex: GET:/v1/orders/pricing.
Passo a passo: criar seu primeiro mock
1
Clique em + Novo mock na toolbar
2
Escolha o tipo: WebClient Genérico, Por Usuário ou X-MOCK-ID
3
Preencha o ID (ou endpointId para Por Usuário) e o payload JSON de resposta
4
Certifique-se que o mock está Ativo e clique em Salvar
5
Configure o serviço conforme a aba do tipo escolhido e rode localmente
Estrutura base de qualquer mock
{
  "_id":        "identificador-unico",      // chave de busca
  "type":       "webclient|external|xmock", // tipo (salvo automaticamente)
  "description":"Descrição legível",
  "enabled":    true,                       // false = mock ignorado
  "payload":    { ... },                    // resposta retornada
  "externalMockProperties": null            // apenas para tipo "external"
}
Papel atual: fallback do Por Usuário

O WebClient Genérico não é um mecanismo separado — ele opera dentro do mesmo client mock que usa GetExternalMockById. Quando a busca por usuário retorna null, o GetExternalMockByIdImpl tenta uma segunda busca usando o próprio endpointId como _id:

// GetExternalMockByIdImpl — lógica interna
val mock =
    mockRepository.findExternalMockByEndpointIdAndAllowedUsersContainsAndEnabledTrue(
        endpointId, userIdentifier          // 1ª tentativa: Por Usuário
    ) ?: mockRepository.findMockByIdAndEnabledTrue(endpointId)  // 2ª: fallback genérico
    ?: return null
Passo 1 — O client mock já existe (mesmo do Por Usuário)

Não há configuração separada. O fallback genérico é ativado automaticamente quando o client mock já está em uso com GetExternalMockById:

// application-local.yml — mesmo que Para Por Usuário
mocks:
  pricing:
    enabled: true
Passo 2 — Criar o mock genérico no Manager

Selecione + Novo mock → 🌐 WebClient. O ID deve ser idêntico ao endpointId usado no client mock (e nos mocks Por Usuário do mesmo endpoint):

{
  "_id": "GET:/v1/orders/pricing",   // idêntico ao endpointId do client
  "type": "webclient",
  "description": "Fallback genérico para precificação",
  "enabled": true,
  "payload": {
    "orderId": "qualquer",
    "discount": 0,
    "finalPrice": 100.00
  },
  "externalMockProperties": null
}
Cenário completo: Por Usuário + Fallback
// client mock chama:
getExternalMockById.execute(
    endpointId = "GET:/v1/orders/pricing",
    userIdentifier = orderId    // ex: "order-999" (não cadastrado)
)

// GetExternalMockByIdImpl executa:
// 1. busca { endpointId: "GET:/v1/orders/pricing", allowedUsers: { $in: ["order-999"] } }
//    → null (order-999 não está em nenhum allowedUsers)
// 2. busca { _id: "GET:/v1/orders/pricing", enabled: true }
//    → retorna o mock genérico ✓
⚠️ O _id do WebClient Genérico deve ser exatamente igual ao endpointId passado na chamada execute(endpointId = "...") — incluindo o método HTTP e o caminho completo, sem query params.
Como funciona

O client mock injeta GetExternalMockById e, antes de fazer a chamada real, consulta o MongoDB filtrando por endpointId + identificador do recurso (orderId, userId, etc). Se encontrar, retorna o payload sem chamar a API externa.

Passo 1 — Criar duas implementações do client
// Interface
interface OrderPricingClient {
    fun getPricing(orderId: String): OrderPricingDto
}

// Implementação REAL (usada fora do local)
@Service
@ConditionalOnProperty("mocks.pricing.enabled", havingValue = "false", matchIfMissing = true)
class OrderPricingClientImpl(
    @Value("\${client.pricing.url}") private val url: String
) : OrderPricingClient, AbstractWebClient(url) {

    override fun getPricing(orderId: String): OrderPricingDto {
        return getClient(WebClientConstants.CONTENT_TYPE_APPLICATION_JSON)
            .get()
            .uri("/v1/orders/pricing?orderId=$orderId")
            .retrieve()
            .bodyToMono(OrderPricingDto::class.java)
            .block()!!
    }
}

// Implementação MOCK (usada localmente)
@Service
@ConditionalOnProperty("mocks.pricing.enabled", havingValue = "true")
class OrderPricingClientMock(
    private val getExternalMockById: GetExternalMockById
) : OrderPricingClient {

    override fun getPricing(orderId: String): OrderPricingDto {
        return getExternalMockById.execute(
            endpointId = "GET:/v1/orders/pricing",
            userIdentifier = orderId,
            clazz = OrderPricingDto::class.java
        ) ?: throw MockNotFoundException(orderId, "GET:/v1/orders/pricing")
    }
}
Passo 2 — Ativar no yml local
// application-local.yml
mocks:
  pricing:
    enabled: true
Passo 3 — Criar o mock no Manager

Selecione + Novo mock → 👤 Por Usuário. Preencha o EndpointId igual ao usado no client e os identificadores em Usuários permitidos:

{
  "_id": "mock-pricing-order-001",   // qualquer nome único
  "type": "external",
  "description": "Mock precificação para order-001",
  "enabled": true,
  "payload": {
    "orderId": "order-001",
    "discount": 10.5,
    "finalPrice": 89.50
  },
  "externalMockProperties": {
    "endpointId": "GET:/v1/orders/pricing",   // deve ser idêntico ao client
    "allowedUsers": ["order-001", "order-002"] // identificadores atendidos
  }
}
Query executada no MongoDB
db.mocks.findOne({
  "externalMockProperties.endpointId": "GET:/v1/orders/pricing",
  "externalMockProperties.allowedUsers": { "$in": ["order-001"] },
  "enabled": true
})
💡 Crie um mock por grupo de usuários com payloads diferentes. Para cobrir todos os outros identificadores automaticamente, crie um 🌐 WebClient Genérico com _id igual ao endpointId — ele será o fallback automático via GetExternalMockByIdImpl.
Como funciona

O MockInterceptor está ativo em todos os perfis exceto production. Ele verifica o header X-MOCK-ID em toda requisição recebida. Se encontrar, busca o mock no MongoDB e retorna o payload sem executar nenhuma lógica de negócio.

Passo 1 — Nenhuma configuração necessária

O interceptor já existe no projeto:

@Component
@Profile("!production")
class MockInterceptor(
    private val getInternalMockById: GetInternalMockById,
    private val objectMapper: ObjectMapper
) : HandlerInterceptor {

    override fun preHandle(
        request: HttpServletRequest,
        response: HttpServletResponse,
        handler: Any
    ): Boolean {
        val mockHeader = request.getHeader("X-MOCK-ID") ?: return true
        val mock = getInternalMockById.execute(mockHeader) ?: return true
        response.status = 200
        response.contentType = "application/json;charset=UTF-8"
        response.writer.write(objectMapper.writeValueAsString(mock))
        return false   // interrompe a cadeia — controller não é chamado
    }
}
Passo 2 — Criar o mock no Manager

Selecione + Novo mock → 🔖 X-MOCK-ID. O ID pode ser qualquer nome único:

{
  "_id": "checkout-mock",
  "type": "xmock",
  "description": "Mock resposta de checkout aprovado",
  "enabled": true,
  "payload": {
    "data": {
      "checkout": {
        "orderId": "order-001",
        "approved": true,
        "status": "PENDING"
      }
    }
  },
  "externalMockProperties": null
}
Passo 3 — Usar nas chamadas
// Via curl
curl -X POST http://localhost:8080/my-service/checkout   -H "X-MOCK-ID: checkout-mock"   -H "Content-Type: application/json"   -d '{"orderId": "order-001"}'

// Via WebClient/RestTemplate em testes
webClient.post()
    .uri("/checkout")
    .header("X-MOCK-ID", "checkout-mock")
    .bodyValue(request)
    .retrieve()
    .bodyToMono(CheckoutResponseDto::class.java)
Query executada no MongoDB
db.mocks.findOne({ _id: "checkout-mock", enabled: true })
// Retorna apenas o campo "payload" do documento
💡 Para GraphQL, estruture o payload com data.nomeQuery conforme o contrato. Use o botão ⚡ Extrair payload no formulário para gerar automaticamente a partir de uma resposta real.
As duas collections Kafka
📥 kafka_messages_mock_inbound

Eventos que o serviço vai consumir como se fossem mensagens Kafka recebidas. Você cria o evento aqui e o serviço o processa.

📤 kafka_messages_mock

Mensagens que o serviço publicou no Kafka durante ambiente local. Somente leitura — serve para inspecionar o que foi enviado.

Passo a passo: disparar um evento de entrada
1
Selecione a collection kafka_messages_mock_inbound na tela de login
2
Clique em + Novo mock e preencha tópico, key e payload do evento
3
Clique em Enviar Evento — o documento é inserido com processed: false
4
O serviço faz polling nessa collection e processa eventos com processed: false, marcando-os como true após consumir
5
Para reprocessar um evento já consumido, clique em ↺ Reprocessar — isso reseta o campo processed para false
Estrutura do documento inbound
{
  "topic":     "order-created",             // tópico Kafka simulado
  "key":       "order-001",                 // chave da mensagem (opcional)
  "payload":   { "orderId": "order-001", "total": 99.90 },
  "processed": false,                       // false = aguardando consumo
  "createdAt": "2024-01-15T10:00:00.000Z"
}
Dica: datas no payload

O formulário converte automaticamente strings de data para o formato numérico que o serviço espera:

// No formulário você escreve:
"date": "2024-01-15"          →  dias desde epoch (ex: 19737)
"timestamp": "2024-01-15T10:00:00Z"  →  milissegundos (ex: 1705312800000)
Estrutura do documento outbound (somente leitura)
{
  "topic":     "order-confirmed",
  "key":       "order-001",
  "value":     { "orderId": "order-001", "status": "CONFIRMED" },
  "timestamp": "2024-01-15T10:05:00.000Z"
}
💡 Use 📋 Usar como modelo em um evento existente para criar variações rapidamente sem preencher tudo do zero.
